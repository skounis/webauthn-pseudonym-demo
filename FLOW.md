# Flow and simulation guide

## Purpose of the demo

This application demonstrates one narrow EUDI Wallet Architecture and Reference Framework (ARF) concept:

> A relying party can register a WebAuthn/FIDO credential as an RP-specific pseudonym and later recognize proof from the same credential.

The demonstration calls that pseudonym **P1**. It shows pseudonymous continuity at one RP. It is not a complete EUDI Wallet implementation.

## What each component represents

| Demo component | Role in the demonstration | What it represents |
| --- | --- | --- |
| Web page (`index.html` and `app.js`) | Requests registration and authentication through the WebAuthn API and transports results to the server | The RP's browser client plus the small part of the flow that a Wallet integration would initiate |
| Browser | Implements `navigator.credentials.create()` and `navigator.credentials.get()` and communicates with an authenticator | The WebAuthn client |
| Microsoft Password Manager | Generates, protects, selects, and uses the passkey credential in the observed test run | The FIDO/WebAuthn authenticator; a stand-in for the Wallet-side cryptographic component |
| Node server (`server.js`) | Creates challenges, verifies WebAuthn responses, and stores public credential information | The relying party and its FIDO server |
| In-memory `p1` object | Holds the RP's record for the demonstration | A very small substitute for the RP's user and credential database |
| `localhost` | Identifies the WebAuthn relying party | The RP ID; a production RP would use its domain |

Microsoft Password Manager is **not** an EUDI Wallet. In this run it replaces only the FIDO authenticator that an EUDI Wallet could implement itself or access as a platform/external authenticator.

The demo does not contain a separate Wallet application. The function name `walletCreatesPseudonym()` marks the conceptual Wallet-side step, but the actual cryptographic operation is delegated through the browser to Microsoft Password Manager.

## Important identifiers

The application uses several values that should not be confused:

### `P1`

`P1` is the human-readable alias used by the demonstration:

```js
alias: 'P1'
```

It makes the flow easy to discuss, but the text `P1` is not itself a cryptographic key.

### User ID

The RP generates an opaque random WebAuthn user handle:

```js
userID: randomBytes(32)
```

It contains no name, email address, PID, or other real-identity information. The RP supplies it during registration. It is not generated by the authenticator and is not the credential key pair.

### Credential ID and public key

Microsoft Password Manager generates a new WebAuthn credential for `localhost`. The credential includes:

- A credential ID that lets the RP and authenticator refer to the credential.
- A public key that the RP uses to verify future signatures.
- A private key that remains protected by the authenticator.

In the ARF-style interpretation used by this demo, the credential ID and associated public key form the meaningful RP-specific pseudonym credential. The RP stores them under the friendly alias `P1`.

## Registration: creating and providing P1

### 1. Client requests registration information

`registerP1WithRP()` in `app.js` requests:

```text
GET /register/options
```

The server creates WebAuthn registration options in `server.js`. They include:

- RP name: `ARF Pseudonym Demo RP`
- RP ID: `localhost`
- Opaque user ID
- Friendly alias: `P1`
- A fresh, unpredictable challenge
- Accepted public-key algorithms

The challenge prevents an old registration response from being replayed.

### 2. Simulated Wallet-side operation requests key creation

`registerP1WithRP()` passes the options to:

```js
walletCreatesPseudonym(registrationOptions)
```

That function calls:

```js
navigator.credentials.create({ publicKey: registrationOptions })
```

Responsibility is divided as follows:

```text
Application code
    asks for a WebAuthn credential
        ↓
Browser WebAuthn client
    validates and forwards the request
        ↓
Microsoft Password Manager
    asks for user approval
    generates the credential ID and key pair
    protects the private key
```

The “Create a passkey” dialog is therefore the authenticator asking the user to approve credential creation. `P1` and `localhost` appear because they were included in the RP's registration options.

### 3. Authenticator returns public registration information

After approval, the authenticator returns a WebAuthn registration response through the browser. It contains the credential ID, information from which the server obtains the public key, authenticator data, client data, and an attestation response.

The private key is not returned to `app.js` and is not sent to the server.

`credentialToJSON()` converts binary WebAuthn fields into base64url strings so that they can be transported as JSON.

### 4. Client sends the initial information to the RP

`registerP1WithRP()` sends the registration response to:

```text
POST /register/verify
```

The RP verifies, among other things, that:

- The response is valid.
- It answers the challenge previously issued by this RP.
- Its origin is `http://localhost:3000` by default.
- Its RP ID is `localhost`.

After successful verification, the server stores:

```js
p1.credential = result.registrationInfo.credential;
```

That record contains the credential ID, public key, signature counter, and transport information. It represents what the RP knows as P1. Storage is only in memory, so restarting the server removes the RP record.

## Authentication: reusing P1 at the same RP

### 1. Client requests a new authentication challenge

`reuseP1AtSameRP()` requests:

```text
GET /login/options
```

The server requires P1 to have been registered. It creates a fresh challenge and puts P1's stored credential ID into `allowCredentials`.

This tells the browser/authenticator which previously registered credential the RP will accept.

### 2. Authenticator finds and reuses the credential

The client calls:

```js
navigator.credentials.get({ publicKey: authenticationOptions })
```

Unlike `navigator.credentials.create()`, this does not create a new pseudonym. Microsoft Password Manager finds the credential registered for the combination of:

- RP ID `localhost`
- P1's credential ID

After user approval, it signs data containing the fresh authentication challenge using the existing private key.

### 3. Client sends the proof to the RP

`reuseP1AtSameRP()` sends the authentication response to:

```text
POST /login/verify
```

The RP checks that the returned credential ID is P1's registered credential and verifies the signature with P1's stored public key. It also verifies the challenge, origin, RP ID, and authenticator data.

Successful verification means:

> The current interaction was authorized using the private key corresponding to the credential previously registered as P1.

This is how the RP recognizes pseudonymous continuity.

## What is real and what is simulated

### Real WebAuthn/FIDO behavior

- The browser uses the real WebAuthn API.
- Microsoft Password Manager acts as a real WebAuthn authenticator.
- A real asymmetric credential is created.
- The private key is kept away from the website and RP server.
- Registration and authentication responses are cryptographically verified.
- Authentication uses a fresh challenge and a real signature.

### Simplified or simulated behavior

- There is no actual EUDI Wallet application.
- Microsoft Password Manager stands in for the FIDO authenticator used by the Wallet flow.
- The RP supports only one in-memory pseudonym record.
- `P1` is hard-coded rather than chosen and managed through Wallet UI.
- There is no database, account management, session, recovery, or production security configuration.
- The RP is `localhost`, not a registered production domain.
- The demo requests no authenticator attestation (`attestationType: 'none'`).

## What successful login does and does not prove

It proves that the authentication response was produced using the credential corresponding to the public key stored as P1.

It does not by itself prove:

- The user's legal or civil identity.
- That P1 is bound to a PID or attested attribute.
- That a certified, genuine, or non-revoked EUDI Wallet Unit participated.
- That the same physical device was used. A synchronized passkey can be available on multiple devices.
- That the user is anonymous. Network data, account activity, attributes, or other information may still identify or correlate the user.
- Unlinkability between repeated interactions at this RP. Those interactions are deliberately linkable as P1.

“The same credential controller returned” is therefore more accurate than “the same person” or “the same physical Wallet Unit returned.”

## Code map

| Stage | Client code (`app.js`) | RP code (`server.js`) |
| --- | --- | --- |
| Prepare registration | `registerP1WithRP()` | `GET /register/options` |
| Create credential | `walletCreatesPseudonym()` and `navigator.credentials.create()` | No key creation occurs at the RP |
| Provide initial credential information | `credentialToJSON()` and `POST /register/verify` | Verify response and assign `p1.credential` |
| Prepare repeat login | `reuseP1AtSameRP()` | `GET /login/options` with P1 in `allowCredentials` |
| Reuse credential | `navigator.credentials.get()` | RP issues a fresh challenge |
| Verify continuity | `POST /login/verify` | Verify signature using P1's stored public key |
